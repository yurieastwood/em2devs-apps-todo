    Code Quality — Analyzers, Formatters, Hooks, Conventional Commits/Branches

    Mar 5, 2026

    ACCEPTED

    Yuri Eastwood

    Context and Problem Statement¶

    A codebase maintained by multiple contributors accumulates style inconsistencies, suppressible linting warnings, and ad-hoc commit messages unless quality gates are enforced automatically. Manual code review is insufficient for mechanical quality concerns — reviewers should focus on logic and architecture, not formatting or naming conventions. Additionally, conventional commit messages and branch names are prerequisites for automated changelog generation and predictable release management. Which code quality tools, enforcement points, and conventions should be adopted across the .NET backend and SvelteKit frontend?

    Decision Drivers¶

    • Automated enforcement: quality rules must be enforced by tooling, not by convention or reviewer vigilance
    • Pre-commit/pre-push validation: formatting and linting errors should be caught locally before a push, not only in CI
    • CI enforcement: the pipeline must act as the final authority — what passes CI is what is acceptable
    • Consistent style: the same style rules must apply whether a developer uses VS Code, Rider, or Visual Studio
    • Conventional changelog support: commit messages must follow a machine-parseable format to enable automated changelog and release note generation
    • Dual-stack coverage: both .NET (C#) and SvelteKit (TypeScript/Svelte) require their own idiomatic toolchains

    Considered Options¶

    • Backend static analysis: SonarAnalyzer + StyleCop.Analyzers vs. Roslynator vs. analyzer-only approach
    • Backend formatting: dotnet format (built-in) vs. CSharpier
    • Frontend linting: ESLint + eslint-plugin-svelte vs. Biome
    • Frontend formatting: Prettier + prettier-plugin-svelte vs. Biome
    • Git hooks: Husky + lint-staged vs. lefthook vs. no hooks (CI-only enforcement)
    • Commit convention: Conventional Commits vs. no enforced format

    Decision Outcome¶

    Chosen option: "Multi-layer enforcement — analyzers and formatters per stack, Husky + lint-staged for local hooks, Conventional Commits enforced via commitlint, and conventional branch naming enforced in both pre-push hook and CI", because it places quality checks at the earliest possible point (staged file check on commit), prevents bad commits from entering the remote (pre-push branch name check), and provides a CI safety net that is authoritative.

    Backend (.NET) quality layer:

    Tool Role
    .editorconfig Defines indentation, line endings, naming rules, and code style; enforced by the Roslyn compiler — violations are build warnings or errors, not just style suggestions
    dotnet format Auto-formatter; run on staged files by pre-commit hook; CI runs dotnet format --verify-no-changes to fail on any deviation
    SonarAnalyzer.CSharp Static analysis for bugs, code smells, security hotspots, and complexity — Roslyn-based, runs on every build
    StyleCop.Analyzers Additional style rules (XML documentation, member ordering, file layout); configured in .editorconfig
    Directory.Build.props Centralises NuGet versions for all analyzer packages; sets <TreatWarningsAsErrors>true</TreatWarningsAsErrors> for release builds

    Frontend (SvelteKit) quality layer:

    Tool Role
    ESLint + eslint-plugin-svelte Linting for TypeScript and Svelte components — catches unused variables, accessibility violations, Svelte-specific anti-patterns
    Prettier + prettier-plugin-svelte Opinionated formatting for .ts, .svelte, .json, .css files
    svelte-check Type-checking for .svelte files using the TypeScript compiler; run in CI to surface type errors in component props and bindings

    Git hooks (Husky + lint-staged):

    Pre-commit hook runs lint-staged, which applies formatters and linters only to staged files — not the entire codebase. This keeps the hook fast even in a large monorepo.

    Pre-commit (lint-staged):
  *.cs          →  dotnet format (format staged .cs files)
  *.ts, *.svelte →  prettier --write, eslint --fix
  *.json, *.css  →  prettier --write

    Pre-push hook validates that the branch name matches the conventional branch pattern before the push reaches the remote:

    Allowed branch patterns:
  feat/<short-description>
  fix/<short-description>
  chore/<short-description>
  hotfix/<short-description>
  release/<version>
  main

    Conventional Commits are enforced via commitlint (@commitlint/config-conventional) in a commit-msg hook. The allowed types are: feat, fix, docs, style, refactor, test, chore, perf, ci, build, revert. This enables automated changelog generation with conventional-changelog or release-please.

    Example valid commit messages:

    feat(achievements): add streak freeze power-up
fix(api): return 404 when todo not found instead of 500
chore(deps): bump SonarAnalyzer.CSharp to 9.32

    CI enforcement (ref: ADR-011):

    • lint job: dotnet format --verify-no-changes, eslint, prettier --check, svelte-check
    • PR branch name validated against conventional branch pattern on PR creation event
    • PR title validated against Conventional Commits format (used as squash-merge commit message)

    Positive Consequences¶

    • Formatting debates are eliminated — dotnet format and Prettier produce deterministic output; there is no room for style bikeshedding in code review
    • SonarAnalyzer catches a meaningful class of bugs (null dereference, resource leak, improper exception handling) at build time rather than in production
    • Conventional commit messages enable automated changelog generation and release tagging via release-please or conventional-changelog without manual curation
    • lint-staged applies hooks only to staged files, keeping the pre-commit hook under one second for typical change sizes
    • Directory.Build.props ensures all .NET projects share the same analyzer versions — no project silently running an older version with different rules

    Negative Consequences¶

    • The initial Husky and lint-staged setup requires all developers to run npm install (or equivalent) after cloning to activate the hooks; a developer who skips this step will not have local enforcement until they notice it
    • TreatWarningsAsErrors for SonarAnalyzer in release builds can surface unexpected build failures when a new analyzer rule is added in a package update; analyzer package updates must be reviewed before merging
    • commitlint in the commit-msg hook will reject commits that do not follow Conventional Commits; developers unfamiliar with the format will encounter rejection messages and need to amend their first few commits

    Neutral¶

    • Husky is configured via a prepare npm script that runs automatically on npm install; developers using non-npm tooling (e.g., pnpm, Bun) must ensure the prepare script is also executed
    • svelte-check reports both type errors and accessibility hints; accessibility hint level can be configured via the --threshold flag if it becomes too noisy

    Pros and Cons of the Options¶

    SonarAnalyzer + StyleCop.Analyzers (chosen)¶

    Both are Roslyn-based, run during dotnet build, and integrate with IDEs that support the Roslyn analyzer protocol (VS Code + C# extension, Rider, Visual Studio).

    • Good, because violations appear inline in the IDE during development — no separate run step required
    • Good, because SonarAnalyzer covers a broad set of quality categories: bugs, vulnerabilities, code smells, complexity
    • Good, because StyleCop enforces documentation and member ordering rules that Sonar does not cover
    • Bad, because the combined analyzer set can produce a large initial warning volume on a new codebase; a triage session is needed to set the appropriate severity levels

    Roslynator¶

    A comprehensive Roslyn analyser and refactoring pack from JB Roslan.

    • Good, because large rule set covering refactoring suggestions beyond what StyleCop covers
    • Bad, because significant overlap with SonarAnalyzer; running both creates noise and potential rule conflicts
    • Bad, because less commonly used than SonarAnalyzer in enterprise .NET teams; fewer community resources

    CSharpier vs. dotnet format¶

    CSharpier is an opinionated formatter (similar to Prettier's philosophy) that reformats entire files with no style configuration. dotnet format reads .editorconfig and applies those rules.

    • dotnet format chosen because it respects the team's .editorconfig rules and is built into the .NET SDK — no additional tool install required
    • CSharpier: good for zero-config formatting; bad because it ignores .editorconfig and may produce style that conflicts with StyleCop rules configured there

    Biome vs. ESLint + Prettier¶

    Biome is a single Rust-based tool that covers both linting and formatting for TypeScript/JavaScript.

    • Biome good, because a single tool replaces both ESLint and Prettier; fast execution
    • Biome bad, because eslint-plugin-svelte provides Svelte-specific rules that Biome does not yet support (as of project inception); Svelte component linting would have gaps
    • ESLint + Prettier chosen because eslint-plugin-svelte and prettier-plugin-svelte have mature Svelte support with established rule sets

    Husky + lint-staged vs. lefthook vs. CI-only¶

    • Husky is the most widely adopted git hook manager in the JS ecosystem; integrates with npm prepare for automatic installation
    • lefthook is a Go-based alternative with better performance for large repos; considered but not chosen as the ecosystem is smaller and the performance difference is negligible at this project's scale
    • CI-only enforcement was rejected because it delays feedback: a developer discovers a lint error only after pushing and waiting for CI, rather than immediately on commit
