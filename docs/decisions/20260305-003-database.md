# Database — PostgreSQL with JSONB

- Status: Accepted
- Date: 2026-03-05

## Context and Problem Statement

EM2Devs.Todo needs to persist two broad categories of data: structured relational data (users, todo items, projects, due dates, completion status) and flexible, schema-evolving gamification data (achievement definitions, user progress snapshots, activity feeds, badge metadata, XP event logs). The challenge is that gamification schemas tend to evolve rapidly during product development while relational data benefits from strict type constraints and referential integrity. Which database strategy best serves both needs without excessive operational complexity?

## Decision Drivers

- Data integrity: relational data must have enforced constraints, foreign keys, and type safety
- Schema flexibility: gamification data structures will evolve frequently; migrations must not block iteration
- Query performance: the application must efficiently query both structured and semi-structured data in the same request
- Operational simplicity: minimise the number of distinct database systems to operate and monitor
- Ecosystem: quality of ORM/driver support in the .NET ecosystem
- Cost: self-hostable, with no per-row or per-operation pricing at the managed cloud tier

## Considered Options

- PostgreSQL (single database, JSONB for flexible columns)
- Polyglot persistence: MongoDB for gamification data + PostgreSQL for relational data
- SQL Server (managed on Azure)
- SQLite (embedded, for local/single-instance use)

## Decision Outcome

Chosen option: "PostgreSQL with JSONB", because a single PostgreSQL instance covers both relational and document-style needs. JSONB columns provide indexed, queryable semi-structured storage for gamification payloads, delivering approximately 90% of what a dedicated document store would offer without the operational cost of running and synchronising two separate database systems. PostgreSQL's GIN indexes on JSONB enable efficient querying of nested gamification data. The .NET ecosystem has first-class support via EF Core with Npgsql.

### Positive Consequences

- Single database engine to operate, monitor, back up, and restore
- JSONB columns give gamification schemas room to evolve without blocking migrations on all related tables
- GIN indexes on JSONB allow targeted queries into achievement progress and activity feed entries
- Full ACID transactions span both relational and JSONB data — no cross-database consistency problems
- EF Core + Npgsql supports JSONB mapping with `UseJsonb()` on owned entity types
- PostgreSQL is open-source, freely hostable, and available as a managed service on every major cloud

### Negative Consequences

- JSONB queries are less ergonomic than a native document store API when deeply nested access is required
- Lack of schema enforcement on JSONB columns means the application layer must validate gamification payloads
- Large JSONB documents stored in hot tables can increase table bloat; requires periodic `VACUUM` tuning for high-write gamification event tables

### Neutral

- Schema migrations (via EF Core migrations or Flyway) apply to the relational columns; JSONB columns evolve through application-level versioning conventions
- If gamification data volume becomes extreme in the future, a dedicated time-series or document store can be introduced incrementally — the relational core stays in PostgreSQL

## Pros and Cons of the Options

### PostgreSQL with JSONB

A single relational database where flexible gamification data lives in indexed JSONB columns alongside strongly-typed relational tables.

- Good, because one database = one connection pool, one backup strategy, one monitoring target
- Good, because ACID transactions span structured and JSONB data — critical for consistent XP award + achievement unlock sequences
- Good, because GIN-indexed JSONB enables efficient queries into activity feeds and achievement progress without a full table scan
- Good, because Npgsql and EF Core provide strong .NET support, including LINQ-to-JSONB query translation
- Good, because open-source with no licensing cost; first-class managed offering on AWS (RDS), Azure (Flexible Server), GCP (Cloud SQL), and Supabase
- Bad, because deeply nested JSONB access is more verbose than a native document API
- Bad, because application layer must enforce schema consistency within JSONB columns

### Polyglot Persistence (MongoDB + PostgreSQL)

Use MongoDB Atlas or a self-hosted replica set for gamification documents and PostgreSQL for relational data.

- Good, because MongoDB's native document model and query language are purpose-built for nested, flexible schemas
- Good, because MongoDB Change Streams enable real-time gamification event propagation with no additional infrastructure
- Bad, because two databases double the operational surface: two connection pools, two backup strategies, two monitoring pipelines, two sets of cloud costs
- Bad, because cross-database transactions are not natively supported; distributed saga patterns add significant complexity to XP award + achievement unlock sequences
- Bad, because two ORMs/drivers must be maintained (.NET EF Core for PostgreSQL + MongoDB .NET Driver), increasing dependency surface
- Bad, because premature optimisation — JSONB is sufficient for the anticipated gamification data volumes at this stage

### SQL Server

Microsoft's relational database with JSON support via `JSON_VALUE`/`OPENJSON`.

- Good, because tight Azure integration and Azure SQL Managed Instance simplify managed hosting on Azure
- Good, because JSON functions cover basic semi-structured data needs
- Bad, because licensing costs (even on Azure) are higher than PostgreSQL at equivalent compute tiers
- Bad, because `JSON_VALUE` / `OPENJSON` are less capable than PostgreSQL JSONB (no GIN indexing equivalent; no native JSON type — stored as `nvarchar`)
- Bad, because less value delivered per dollar compared to PostgreSQL for this project's requirements

### SQLite

An embedded, serverless relational database suitable for local development and single-node deployments.

- Good, because zero operational overhead; the database is a file
- Good, because excellent for local development and integration tests
- Bad, because concurrent write throughput is limited by a single write-ahead log; not suitable for multi-user production workloads
- Bad, because JSONB equivalents are limited; JSON functions exist but lack indexing depth
- Bad, because no native network access; cannot be shared across multiple backend instances
