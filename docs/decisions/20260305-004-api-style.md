# API Style — REST Minimal APIs + SignalR + Scalar API Docs

- Status: Accepted
- Date: 2026-03-05

## Context and Problem Statement

EM2Devs.Todo needs an API layer that covers two distinct communication patterns: standard CRUD operations for todos, users, achievements, and quests; and real-time push of gamification events (XP awarded, achievement unlocked, leaderboard updated) to connected clients. A single protocol choice must cover both patterns, or a well-defined combination must be selected. What API style and tooling should back the EM2Devs.Todo backend?

## Decision Drivers

- Resource model clarity: todos, users, achievements, and quests map cleanly to discrete resources
- Real-time capability: gamification events must reach the client within seconds of the triggering domain event, without polling
- .NET 9 first-class support: prefer solutions that align with the investment direction of the .NET team
- OpenAPI generation and developer experience: API surface must be explorable and documented out of the box
- Frontend integration: the SvelteKit frontend needs both a typed HTTP client and a real-time event stream
- Scalability: the real-time layer must support horizontal scaling with a backplane

## Considered Options

- REST with .NET 9 Minimal APIs + SignalR + Scalar
- REST with ASP.NET Core Controllers + SignalR + Swagger UI
- GraphQL (Hot Chocolate) with subscriptions

## Decision Outcome

Chosen option: "REST with .NET 9 Minimal APIs + SignalR + Scalar", because it combines the leanest possible HTTP API surface for resource operations with a first-class real-time push channel, uses tooling that .NET 9 is directly investing in, and avoids framework overhead that is not justified by the resource model of this application.

The layers of the chosen approach are:

- **Minimal APIs** handle all CRUD endpoints. Route groups (`RouteGroupBuilder`) keep endpoint registration organised by feature. `TypedResults` make return types explicit and contribute to accurate OpenAPI schema generation.
- **SignalR Hub** (`GameHub`) receives domain events published from the CQRS pipeline — `TodoCompleted -> XpAwarded -> AchievementUnlocked` — and pushes them to the appropriate connected clients using groups (per-user and global leaderboard).
- **Redis backplane** ([ADR-008](20260305-008-caching.md)) is wired to SignalR from day one so that adding a second API instance does not break real-time delivery.
- **Scalar** replaces Swagger UI as the interactive API documentation explorer. .NET 9 ships `Microsoft.AspNetCore.OpenApi` for document generation; Scalar provides the UI layer. It is actively recommended by Microsoft for .NET 9+ projects.

### Positive Consequences

- Minimal APIs reduce boilerplate per endpoint and make the API surface easy to read and navigate
- .NET 9 built-in OpenAPI generation (`Microsoft.AspNetCore.OpenApi`) is maintained by the .NET team — no third-party Swashbuckle dependency needed
- Scalar provides a modern, interactive API explorer that is easier to use than Swagger UI and renders well on large schemas
- SignalR's hub model cleanly separates the real-time channel from the HTTP layer; clients subscribe to exactly the events they need
- The Redis backplane means horizontal scaling is possible without rearchitecting the real-time layer
- Route groups keep Minimal API registration organised as the surface grows

### Negative Consequences

- Two protocols (HTTP and WebSocket/SignalR) means the frontend must manage two connection types and their lifecycle independently
- SignalR adds a persistent connection overhead per active client; connection limits must be monitored as user count grows
- Scalar is newer than Swagger UI and has a smaller community surface, though it is well-maintained and backed by a dedicated team

### Neutral

- Minimal APIs and Controllers coexist in a .NET 9 project if legacy or third-party middleware requires controllers; this is not a binary lock-in
- SignalR falls back to long-polling transparently when WebSocket connections are unavailable (e.g., certain proxies), which maintains compatibility at the cost of some efficiency

## Pros and Cons of the Options

### REST with .NET 9 Minimal APIs + SignalR + Scalar

Lean HTTP endpoints for resource operations, a dedicated real-time hub for gamification events, and a modern documentation UI. All three are actively developed and aligned with .NET 9 investment priorities.

- Good, because Minimal APIs are the primary pattern the .NET team is investing in for .NET 9+
- Good, because `Microsoft.AspNetCore.OpenApi` generates accurate OpenAPI documents without third-party packages
- Good, because SignalR is the mature, .NET-native real-time library with built-in fallback transports and backplane support
- Good, because Scalar is recommended by Microsoft for .NET 9 projects and provides a significantly better DX than Swagger UI
- Good, because route groups and endpoint filters keep API code organised without the controller ceremony
- Bad, because two protocols increase client complexity compared to a single protocol solution

### REST with ASP.NET Core Controllers + SignalR + Swagger UI

The traditional .NET API style. Well-understood and widely documented.

- Good, because controllers are familiar to developers with pre-.NET 6 experience
- Good, because attribute routing and action filters are well-documented and have broad ecosystem support
- Bad, because controllers introduce more ceremony (class per controller, constructor injection boilerplate) without adding capability for this use case
- Bad, because Swashbuckle (Swagger UI provider) is no longer actively maintained for .NET 9 and has been dropped from the default template
- Bad, because the .NET team's investment is clearly moving toward Minimal APIs; choosing controllers creates tech debt from inception

### GraphQL (Hot Chocolate) with Subscriptions

A single graph-based API where subscriptions replace SignalR for real-time events.

- Good, because a single protocol covers both query/mutation and real-time subscription patterns
- Good, because the type system and introspection offer strong self-documentation
- Good, because Hot Chocolate is a mature, actively developed GraphQL server for .NET
- Bad, because GraphQL's strengths (flexible field selection, nested queries) are not needed when the resource boundaries are clear and fixed
- Bad, because Hot Chocolate adds significant dependency weight and a new mental model for a team already fluent in REST
- Bad, because REST is more familiar to the anticipated frontend and mobile consumers; GraphQL requires a GraphQL-aware client
- Bad, because overkill for the current resource surface (todos, users, achievements, quests)
