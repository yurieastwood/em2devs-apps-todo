# Hosting — Containers (Deployment Target TBD)

- Status: Accepted
- Date: 2026-03-05

## Context and Problem Statement

EM2Devs.Todo is in active development. The team needs to decide on a hosting and deployment strategy, but the production cloud target has not yet been chosen. Committing to a specific cloud platform now (Azure App Service, AWS ECS, etc.) risks incurring lock-in costs before requirements — budget, region preferences, existing agreements — are fully understood. At the same time, the project needs a clear path from local development to a production-grade deployment. What hosting strategy allows the team to build confidently without premature cloud lock-in?

## Decision Drivers

- Platform agnosticism: avoid hard dependencies on a single cloud provider's proprietary APIs during development
- Aspire compatibility: the deployment strategy must align with what Aspire generates from the AppHost definition
- Production readiness path: there must be a clear and credible route to production without a major re-architecture
- Cost flexibility: the team should be free to choose the most cost-effective platform when the time comes
- Operational consistency: the same artifact (container image) that runs locally should run in production

## Considered Options

- Containers (Docker) with cloud target deferred
- Azure (App Service or Container Apps)
- AWS (ECS / Fargate)
- Self-hosted (VPS or bare metal)

## Decision Outcome

Chosen option: "Containers with deployment target TBD", because containerising every service (API, worker, frontend) provides a portable, cloud-agnostic artifact that can be deployed to any container platform. Aspire's `AppHost` already models the system as a set of container resources; `azd` can generate Azure Container Apps manifests, and the same AppHost graph can produce a Docker Compose file for any other platform. Deferring the cloud target decision is rational: the work required to switch targets is minimal when the deployment unit is a container image, and the team gains concrete operational experience before committing to a vendor.

When production deployment is imminent, the cloud target will be chosen based on cost, team familiarity, and feature requirements, and a follow-up ADR will record that decision (see "More Information" below).

### Positive Consequences

- Container images run identically in local Aspire orchestration, CI pipelines, and production — no environment-specific surprises
- No cloud-provider SDK calls in application code; switching targets requires only infrastructure changes
- Aspire-generated Docker Compose file is a complete, runnable deployment descriptor for any Docker-capable host
- Azure Container Apps remains the default first-candidate production target due to first-class Aspire/`azd` support, but is not binding
- CI pipeline can build and push images to any registry (GitHub Container Registry, ECR, ACR) without re-work

### Negative Consequences

- Without a fixed cloud target, environment-specific configuration (IAM roles, managed identity, secrets management integration) cannot be fully designed yet; these remain TBD
- Deferring the cloud target means some infrastructure-as-code work will need to be done closer to production deployment
- Self-hosting is a viable option but would require the team to manage container orchestration (Docker Swarm or Kubernetes) — adding operational burden

### Neutral

- The decision to defer does not prevent the team from prototyping on a preferred cloud target during development
- This ADR will be superseded by a follow-up hosting decision ADR once the production target is confirmed

## Pros and Cons of the Options

### Containers (Docker) with Target TBD

Build container images for all services. Defer selection of the production runtime (cloud provider and service tier) until closer to deployment.

- Good, because portable artifact — one image works on any container platform
- Good, because aligns directly with what Aspire generates; no translation layer needed
- Good, because CI/CD pipeline can be built and tested before the cloud target is chosen
- Good, because cost and feature comparisons can be made with a working system rather than estimates
- Bad, because infrastructure-as-code (IaC), secrets management, and networking decisions are deferred; they must be addressed before go-live

### Azure (App Service / Container Apps)

Deploy directly to Azure, using App Service for the API and Static Web Apps for the SvelteKit frontend, or Azure Container Apps for a unified container-based deployment.

- Good, because Azure Container Apps has first-class Aspire support via `azd`; `azd up` can deploy the entire Aspire-defined topology
- Good, because managed identity, Key Vault, and Azure Monitor integration simplify secrets and observability configuration
- Good, because Azure Database for PostgreSQL Flexible Server is a mature managed offering
- Bad, because committing to Azure now forecloses cost comparisons; Azure is not always the cheapest option for small workloads
- Bad, because proprietary integrations (managed identity, Azure Monitor SDK) would create lock-in if introduced too early

### AWS (ECS / Fargate)

Deploy container images to Amazon ECS using Fargate for serverless container compute.

- Good, because Fargate eliminates EC2 instance management; pay-per-task pricing suits variable workloads
- Good, because AWS has the largest global infrastructure footprint and mature container tooling
- Bad, because Aspire does not have a native `azd`-equivalent for ECS; Terraform or CDK IaC must be authored manually
- Bad, because AWS RDS PostgreSQL and Fargate costs can exceed Azure equivalents at small scales

### Self-Hosted (VPS or Bare Metal)

Run containers on a rented VPS (Hetzner, DigitalOcean) using Docker Compose or a lightweight Kubernetes distribution (k3s).

- Good, because lowest infrastructure cost at small scale; predictable monthly pricing
- Good, because full control over the environment; no cloud provider constraints
- Bad, because the team must manage OS updates, TLS certificates, backups, and container orchestration
- Bad, because scaling beyond a single node requires Kubernetes expertise that adds significant operational overhead
