# Caching — Redis via .NET Aspire

- Status: Accepted
- Date: 2026-03-05

## Context and Problem Statement

EM2Devs.Todo includes several categories of read-heavy data that are expensive to recompute on every request: leaderboards aggregate XP across all users, user profiles are fetched on every authenticated API call, and achievement definitions are a fixed catalogue read frequently but updated rarely. Beyond HTTP caching, the app uses SignalR ([ADR-004](20260305-004-api-style.md)) for real-time gamification event delivery. When the API runs as more than one instance — whether for load distribution or fault tolerance — SignalR requires a shared message backplane so that a client connected to instance A receives events published by instance B. What caching solution should be used to satisfy both the read-performance and the real-time backplane requirements?

## Decision Drivers

- Performance for read-heavy queries: leaderboards are computed from aggregate data across the full user table; recomputing on every request is not viable at scale
- Cache invalidation control: the team needs explicit, targeted invalidation (e.g., invalidate the leaderboard cache when any user's XP changes), not just TTL expiry
- SignalR backplane: multi-instance deployments require a pub/sub-capable backplane so SignalR messages are fanned out across all instances
- .NET Aspire integration: the project uses Aspire ([ADR-005](20260305-005-orchestration.md)) for local orchestration; the caching layer should integrate cleanly with the Aspire component model
- Operational simplicity: developers should not need to install and configure a cache server manually; local dev must work out of the box
- Versatility: a single solution should cover both caching and pub/sub to avoid running two separate infrastructure components

## Considered Options

- Redis via Aspire first-party component (`Aspire.StackExchange.Redis`)
- In-memory cache (`IMemoryCache` / `IDistributedCache` with in-memory provider)
- Memcached
- No caching (optimise queries instead)

## Decision Outcome

Chosen option: "Redis via .NET Aspire", because Redis is the only option that satisfies both the distributed caching and SignalR backplane requirements with a single component, and the first-party Aspire integration (`Aspire.StackExchange.Redis`) makes it automatically available during local development without any manual setup.

Redis is used for the following purposes in EM2Devs.Todo:

- **Leaderboard caching**: leaderboard queries (top-N users by XP, weekly/monthly aggregations) are computed and cached in Redis with explicit invalidation when a `XpAwarded` domain event is raised. Cache-aside pattern: check Redis first; on miss, compute from the database and populate the cache.
- **User profile caching**: the authenticated user's profile (display name, avatar, XP total, level, active quest) is cached per user ID. Invalidated on profile update or XP award.
- **Achievement definitions**: the achievement catalogue is a static-ish dataset loaded into Redis at startup and refreshed infrequently (or on admin update). Read path checks Redis; admin writes invalidate the entry.
- **SignalR backplane**: `AddStackExchangeRedis` is called on the SignalR service registration. All `GameHub` messages published by any API instance are fanned out via Redis pub/sub to all other instances, ensuring every connected client receives real-time gamification events regardless of which instance they are connected to.

During local development, Aspire provisions a Redis container automatically as part of the app host. No manual Docker command or local Redis installation is required.

### Positive Consequences

- Leaderboard response times drop significantly: a cache hit returns pre-computed data in sub-millisecond time vs. an aggregation query over the full user table
- SignalR works correctly in multi-instance deployments from day one — no future rearchitecting required when scaling horizontally
- Aspire's container provisioning means every developer has the same Redis version and configuration without manual setup steps
- `Aspire.StackExchange.Redis` registers `IConnectionMultiplexer` in the DI container with health checks, metrics, and tracing wired up automatically
- Redis's rich data structures (sorted sets, hashes) open the option to store leaderboard data natively in Redis rather than computing it from the relational database
- A single Redis instance serves both caching and pub/sub — one infrastructure component to operate

### Negative Consequences

- Redis is a network dependency during local development; if Aspire fails to start the container (e.g., Docker daemon not running), the app cannot start without a fallback
- Redis introduces a new operational component in production; the team must provision, monitor, and back up a Redis instance (or use a managed service such as Azure Cache for Redis)
- Cache invalidation logic must be maintained: as new domain events are added, developers must remember to invalidate relevant cache entries or accept stale data

### Neutral

- `StackExchange.Redis` is the de facto .NET Redis client; the Aspire component wraps it with minimal additional abstraction, so existing `StackExchange.Redis` documentation and patterns apply directly
- Redis persistence (RDB/AOF) is available but not required for cache use cases; if Redis is restarted, the cache is cold and warms up on first request
- Aspire supports both a local container and an existing external Redis connection string, making the transition from local dev to production straightforward

## Pros and Cons of the Options

### Redis via .NET Aspire (`Aspire.StackExchange.Redis`)

A battle-tested distributed cache and pub/sub broker, integrated into the project via the first-party Aspire component. Aspire handles container lifecycle in local dev; production targets a managed Redis service.

- Good, because Redis is the industry-standard solution for distributed caching and pub/sub — abundant documentation, tooling, and operational patterns
- Good, because it is the only option that also satisfies the SignalR backplane requirement without adding a second infrastructure component
- Good, because `Aspire.StackExchange.Redis` wires up health checks, OpenTelemetry tracing, and metrics automatically
- Good, because Aspire provisions the Redis container during local dev — zero manual setup
- Good, because sorted sets make it possible to maintain a live leaderboard natively in Redis if the relational aggregate approach becomes too slow
- Bad, because Docker must be running locally for Aspire to start the Redis container
- Bad, because adds a managed Redis service cost in production (though Azure Cache for Redis Basic tier is inexpensive for early-stage use)

### In-Memory Cache (`IMemoryCache` / `IDistributedCache` in-memory)

The built-in .NET in-process cache. No external dependency; data lives in the process heap.

- Good, because zero infrastructure — no container, no external service, no Docker required
- Good, because trivial to set up (`services.AddMemoryCache()`)
- Good, because the fastest possible read path — data is already in process memory
- Bad, because not shared across instances — each API instance has its own isolated cache, leading to inconsistent reads and duplicate computation when scaled horizontally
- Bad, because cache is lost on every process restart
- Bad, because cannot be used as a SignalR backplane — disqualifying for the multi-instance requirement
- Bad, because memory pressure in the API process increases as cached datasets grow

### Memcached

A high-performance distributed memory cache designed for simple key-value workloads.

- Good, because extremely fast for pure key-value get/set operations
- Good, because well-understood operationally with managed hosting options
- Bad, because no pub/sub capability — cannot serve as a SignalR backplane, requiring a second broker (RabbitMQ, Redis) anyway
- Bad, because no first-party Aspire component; integration requires manual configuration
- Bad, because limited data structure support compared to Redis (no sorted sets, no hashes), restricting future optimisation options
- Bad, because solving both the caching and backplane requirements would require two separate infrastructure components instead of one

### No Caching (Optimise Queries Instead)

Rely entirely on database query optimisation, indexing, and connection pooling to deliver acceptable response times without an external cache.

- Good, because removes all cache invalidation complexity — data is always fresh from the source
- Good, because simpler architecture — fewer moving parts to operate and monitor
- Bad, because leaderboard queries aggregate XP across all users; with even a few thousand users this becomes a full-table aggregation that cannot be optimised away with indexes alone
- Bad, because does not address the SignalR multi-instance problem — a backplane is still required regardless of caching decisions
- Bad, because under load, repeated expensive queries will stress the database and degrade overall response times across all endpoints
