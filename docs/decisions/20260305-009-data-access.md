# Data Access — EF Core (writes) + Dapper (reads)

- Status: Accepted
- Date: 2026-03-05

## Context and Problem Statement

With CQRS separating the command (write) path from the query (read) path, the data access layer can be optimised independently for each concern. The command side handles domain-rich writes — entity creation, state transitions, aggregate persistence — where change tracking, domain modelling, and schema migration support are valuable. The query side handles read-optimised projections — leaderboards, dashboards, achievement summaries — where raw SQL performance and minimal overhead matter more than ORM convenience. Which data access approach should be used for each path?

## Decision Drivers

- CQRS alignment: data access strategy should mirror the command/query split
- Write-side domain modelling: support for change tracking, value objects, owned entities, and relationships
- Read-side performance: ability to write hand-crafted SQL for complex projections without ORM translation overhead
- Migration support: schema evolution must be tracked, auditable, and automatable
- Developer experience: familiar .NET tooling, strong IDE support, good documentation
- Dependency footprint: prefer established, well-maintained libraries without restrictive licensing

## Considered Options

- EF Core only
- Dapper only
- EF Core (writes) + Dapper (reads)
- Marten (document DB on PostgreSQL)

## Decision Outcome

Chosen option: "EF Core (writes) + Dapper (reads)", because each tool is used where it provides the greatest benefit. EF Core handles the command path with full domain modelling, change tracking, relationship navigation, and migration management. Dapper handles the query path with raw SQL, minimal overhead, and direct result mapping — which is critical for complex read projections such as leaderboards and achievement summaries. This is a well-established pattern in .NET CQRS applications.

### Positive Consequences

- Commands retain full EF Core capabilities: change tracking, value objects, owned entities, `SaveChanges` unit of work
- Queries can use raw SQL tuned for read performance — no ORM query translation surprises
- EF Core Migrations provides a single, auditable schema history tracked in `__EFMigrationsHistory`
- Both libraries are battle-tested, open-source, and have strong .NET community support
- Clear architectural boundary: any file in a `Queries/` handler that touches the DB uses Dapper; any `Commands/` handler uses EF Core
- Dapper's lightweight mapping makes it straightforward to project directly into read model DTOs without domain entity overhead

### Negative Consequences

- Developers must understand and respect the boundary — EF Core must not be used for read projections that can be served by Dapper
- Two mental models for SQL interaction (LINQ vs raw SQL) require discipline to keep consistent
- Dapper does not participate in EF Core's Unit of Work; queries must use a separate `IDbConnection`

### Neutral

- Both EF Core and Dapper operate over the same PostgreSQL connection string — no additional infrastructure is introduced
- The boundary between EF Core and Dapper roughly maps to the command/query boundary already established by CQRS, keeping the rule easy to remember and enforce in code review

## Pros and Cons of the Options

### EF Core only

A single ORM for both commands and queries. EF Core's LINQ provider is used for all database interactions, with raw SQL as an escape hatch via `FromSqlRaw` when needed.

- Good, because a single library reduces cognitive load and keeps the data access model uniform
- Good, because change tracking, relationships, and migrations are all in one place
- Good, because strong IDE support for LINQ queries
- Bad, because EF Core query translation can generate suboptimal SQL for complex projections (leaderboards, multi-table aggregates) that are much easier to express and tune as raw SQL
- Bad, because the ORM abstraction adds overhead on the read path where it provides no write-side benefits

### Dapper only

Use Dapper's lightweight SQL mapping for all database interactions, writing raw SQL for both commands and queries.

- Good, because raw SQL gives complete control over query shape and performance on both paths
- Good, because zero ORM overhead across the board
- Bad, because no change tracking means domain-level state management must be implemented manually
- Bad, because no migration tooling — schema evolution requires a separate migration framework
- Bad, because complex domain relationships and value objects require manual mapping boilerplate

### EF Core (writes) + Dapper (reads)

Use EF Core on the command path for domain modelling and migrations, and Dapper on the query path for raw SQL projections.

- Good, because each tool is applied where it is strongest
- Good, because write-side retains full EF Core domain modelling and change tracking
- Good, because read-side projections are fast, explicit, and not subject to ORM translation quirks
- Good, because well-established pattern with strong community precedent in .NET CQRS applications
- Bad, because two data access libraries increase the initial setup surface area
- Bad, because the boundary between EF Core and Dapper must be actively maintained via team convention and code review

### Marten (document DB on PostgreSQL)

Use Marten as a document database and event store abstraction on top of PostgreSQL, replacing both EF Core and Dapper.

- Good, because JSONB document storage is a natural fit for aggregate persistence
- Good, because Marten includes its own event sourcing and projection support
- Good, because single library handles persistence, projections, and schema management
- Bad, because introduces a document DB abstraction over a relational database, adding conceptual complexity when relational modelling with EF Core + JSONB already satisfies our requirements
- Bad, because event sourcing is not a requirement for this project and Marten's added capabilities would be unused complexity
- Bad, because smaller community than EF Core; fewer team members will have prior experience
