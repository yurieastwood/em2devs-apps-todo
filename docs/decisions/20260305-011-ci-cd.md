# CI/CD — GitHub Actions

- Status: Accepted (pipeline structure partially superseded by [ADR-028](20260406-028-pipeline-restructuring.md))
- Date: 2026-03-05

## Context and Problem Statement

The EM2Devs.Todo project needs an automated pipeline that builds, tests, lints, scans, and deploys every change. Without automation, quality gates are manual and inconsistent, and the feedback loop for contributors is slow. The team needs a CI/CD platform that integrates tightly with the code host, supports .NET 9 workloads, and operates within a reasonable cost envelope. Which CI/CD platform should drive the pipeline?

## Decision Drivers

- GitHub integration: the repository is hosted on GitHub; the platform should reduce context-switching and integration friction
- .NET support: native or well-maintained action ecosystem for `dotnet build`, `dotnet test`, `dotnet format`, EF Core migrations
- Cost: free tier availability for a project at this scale; predictable pricing as usage grows
- Container registry support: the pipeline must be able to build and push Docker images without requiring a separate registry platform
- Community ecosystem: reusable actions for common steps (setup-dotnet, caching, Playwright, security scanning)
- Security scanning: the pipeline must include steps for dependency vulnerability checks and SAST

## Considered Options

- GitHub Actions
- Azure DevOps Pipelines
- GitLab CI

## Decision Outcome

Chosen option: "GitHub Actions", because the code is already hosted on GitHub, making Actions the path of least resistance — no separate account, no webhook configuration, no separate secrets store. The `actions/setup-dotnet` action has first-class .NET 9 support, caching is built in via `actions/cache`, and GitHub Container Registry (GHCR) is directly available for Docker image publishing. The ecosystem of community-maintained actions covers every step in the required pipeline without custom scripting.

The pipeline is structured into the following jobs, which run in dependency order:

| Job | Steps |
|-----|-------|
| `build` | Checkout, setup .NET 9, restore NuGet packages, `dotnet build --no-restore` |
| `lint` | `dotnet format --verify-no-changes`, ESLint, Prettier, svelte-check (ref: [ADR-016](20260305-016-code-quality.md)) |
| `test` | Unit tests (xUnit), integration tests via Testcontainers (ref: [ADR-014](20260305-014-testing.md)) |
| `security` | `dotnet list package --vulnerable`, OWASP dependency-check, SAST scan (ref: [ADR-021]) |
| `migrate` | `dotnet ef database update` against a staging DB (ref: [ADR-020]) |
| `deploy` | Build Docker image, push to GHCR, deploy to target environment |

Branch protection rules require `build`, `lint`, `test`, and `security` to pass before any PR can merge.

### Positive Consequences

- Contributors get automated feedback (build status, test results, lint errors) directly in the PR without leaving GitHub
- GHCR eliminates the need for a separate container registry account; images are co-located with the code
- Reusable workflows and composite actions allow pipeline logic to be shared and versioned within the repo
- GitHub-native secrets management keeps credentials out of code with no additional tooling
- Free for public repositories; Actions minutes for private repos scale predictably

### Negative Consequences

- GitHub vendor lock-in: the pipeline syntax (YAML with GitHub-specific expressions) is not portable to other CI platforms without rewrite
- Actions minute limits apply on private repositories; compute-intensive integration tests must be managed to avoid unexpected billing
- GitHub Actions runners use Ubuntu by default; Windows-specific build steps require self-hosted runners or a paid runner tier

### Neutral

- The pipeline configuration lives in `.github/workflows/` within the monorepo (ref: [ADR-015](20260305-015-repo-structure.md)), versioned alongside the code it tests
- PR title validation (conventional commit format for squash-merge) is enforced as a separate workflow job

## Pros and Cons of the Options

### GitHub Actions

The native CI/CD platform for GitHub-hosted repositories, configured via YAML files in `.github/workflows/`.

- Good, because zero additional account setup — triggers, secrets, and environments are all configured in the same GitHub UI used for code review
- Good, because `actions/setup-dotnet` provides .NET 9 support and caching out of the box
- Good, because GHCR provides a free, integrated container registry with the same access control model as the repository
- Good, because free tier is generous for public repositories; community actions cover every required pipeline step
- Bad, because pipeline YAML uses GitHub-specific expression syntax, creating vendor lock-in
- Bad, because compute is limited for private repositories and can incur costs at scale

### Azure DevOps Pipelines

Microsoft's enterprise CI/CD platform, tightly integrated with the Azure ecosystem.

- Good, because first-class .NET support and a mature YAML pipeline syntax
- Good, because strong integration with Azure Container Registry, Azure App Service, and Azure Key Vault
- Bad, because the code lives on GitHub, requiring webhook configuration and cross-platform integration overhead
- Bad, because a separate Azure DevOps organisation must be created, maintained, and billed independently from GitHub
- Bad, because context-switching between GitHub (code review) and Azure DevOps (pipeline results) slows contributor feedback loops

### GitLab CI

A fully integrated DevOps platform with its own Git hosting, CI/CD, container registry, and security scanning.

- Good, because fully integrated platform covers code hosting, CI/CD, registry, and security scanning in one product
- Good, because pipeline syntax (`.gitlab-ci.yml`) is mature and well-documented
- Bad, because the project is hosted on GitHub; adopting GitLab CI would require migrating the repository to GitLab, which is a significant operational change with no corresponding benefit
- Bad, because contributors and stakeholders are already using GitHub workflows (issues, PRs, discussions); fragmenting the toolchain is not justified
