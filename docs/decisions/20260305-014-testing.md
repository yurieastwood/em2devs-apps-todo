# Testing — xUnit + Shouldly + NSubstitute + Testcontainers / Vitest + Playwright

- Status: Accepted
- Date: 2026-03-05

## Context and Problem Statement

EM2Devs.Todo spans a .NET 9 backend (API, application layer, domain, infrastructure) and a SvelteKit frontend. Both require a test strategy that enables confident refactoring, prevents regressions, and exercises integration points (database, cache, auth) with real dependencies where it matters. The testing stack must be open-source licensed for unrestricted commercial use, readable, and well-suited to the Clean Architecture layer structure. A notable constraint is that FluentAssertions — formerly the de facto .NET assertion library — moved to a commercial license in v7+, requiring an alternative assertion library for backend tests.

## Decision Drivers

- Open-source licensing: all test libraries must be usable without commercial licenses or per-deployment fees
- Assertion readability: assertion failures should produce clear, human-readable messages that identify what was expected vs. what was found
- .NET ecosystem maturity: libraries must be actively maintained with broad community adoption
- Container-based integration tests: infrastructure integration tests should exercise a real PostgreSQL instance and Redis cache, not in-memory fakes, to catch driver-level and query-level issues
- Architecture boundary enforcement: the Clean Architecture layer structure must be machine-verifiable to prevent dependency drift
- Frontend testing DX: frontend tooling must integrate with Vite/SvelteKit's build pipeline natively
- E2E coverage: critical user flows must be tested against the real application in a browser

## Considered Options

- Assertion library: Shouldly, FluentAssertions (v7+), TUnit, xUnit built-in Assert
- Mocking library: NSubstitute, Moq
- Integration testing: WebApplicationFactory + Testcontainers, in-memory EF Core provider
- Frontend unit/component: Vitest + Svelte Testing Library, Jest + @testing-library/svelte
- E2E: Playwright, Cypress

## Decision Outcome

Chosen option: "xUnit + Shouldly + NSubstitute + Testcontainers for backend; Vitest + Svelte Testing Library + Playwright for frontend", because this combination covers all test levels with open-source tools, provides readable assertion output, and exercises real infrastructure in integration tests.

**Backend test stack:**

| Tool | Role |
|------|------|
| xUnit | Test runner and framework — industry standard for .NET; first-class support in `dotnet test` and CI |
| Shouldly | Assertion library — open-source, readable `Should()` extension syntax, clear failure messages |
| NSubstitute | Mocking — clean substitute creation syntax; avoids Moq's setup verbosity |
| WebApplicationFactory | ASP.NET Core in-process test host for integration tests |
| Testcontainers | Spins up real PostgreSQL and Redis containers per test session; no in-memory fakes for integration layer |
| NetArchTest | Architecture tests — enforces that Domain has no Infrastructure references, Application has no API references, etc. |

**Frontend test stack:**

| Tool | Role |
|------|------|
| Vitest | Unit/component test runner — Vite-native, shares config with SvelteKit build, fast HMR-aware test execution |
| Svelte Testing Library | Component testing utilities for Svelte — encourages testing behaviour, not implementation |
| Playwright | E2E browser tests — cross-browser, Microsoft-backed, first-class TypeScript support |

**Test project naming convention** (per Clean Architecture layer, ref: [ADR-015](20260305-015-repo-structure.md)):

```
tests/
├── EM2Devs.Todo.Api.UnitTests/
├── EM2Devs.Todo.Application.UnitTests/
├── EM2Devs.Todo.Domain.UnitTests/
├── EM2Devs.Todo.Infrastructure.IntegrationTests/
└── EM2Devs.Todo.E2E/                              # Playwright
```

Architecture tests live in a dedicated project (`EM2Devs.Todo.ArchitectureTests`) that references all production assemblies but contains no application logic.

### Positive Consequences

- Shouldly provides assertion output that reads as natural English (`value.ShouldBe(42)`) and failure messages that immediately identify the discrepancy without requiring a debugger
- Testcontainers ensures integration tests exercise the real PostgreSQL wire protocol, real EF Core migrations, and real Redis client behaviour — bugs invisible with in-memory providers are caught before deployment
- NetArchTest assertions are executable specifications of the Clean Architecture rules; violations fail the CI build rather than requiring manual code review
- Vitest shares the Vite config with SvelteKit, eliminating the configuration drift between the test environment and the build environment
- Playwright's `codegen` tool accelerates E2E test authoring; its trace viewer provides step-by-step replay of failures in CI

### Negative Consequences

- Testcontainers requires Docker to be available on the CI runner; GitHub Actions' default Ubuntu runners satisfy this, but developers on machines without Docker Desktop must install an alternative runtime (e.g., Colima on macOS)
- Shouldly is less widely documented than FluentAssertions; developers familiar with FluentAssertions will need a brief ramp-up period, though the API is similar in structure
- Maintaining separate test runners (xUnit for .NET, Vitest for frontend, Playwright for E2E) means the CI pipeline must configure and cache three distinct toolchains

### Neutral

- xUnit's `[Theory]` + `[InlineData]` / `[MemberData]` provides parameterised test support equivalent to NUnit's `[TestCase]`, covering all common data-driven test scenarios
- Aspire's test project support (Microsoft.Extensions.AspNetCore.Testing) is available for integration tests that need the full Aspire orchestration; this is considered for future adoption as needed

## Pros and Cons of the Options

### Shouldly

A mature open-source assertion library for .NET. Assertion failures include the asserted expression, expected value, and actual value in a human-readable format.

- Good, because open-source with no commercial licensing restrictions
- Good, because `Should()` extension method syntax reads naturally: `result.ShouldBe(expected)`, `collection.ShouldContain(item)`
- Good, because failure messages include the source expression, reducing time spent reading stack traces
- Good, because actively maintained with .NET 9 support
- Bad, because smaller community than FluentAssertions; fewer blog posts and Stack Overflow answers reference it directly

### FluentAssertions (v7+)

The formerly dominant .NET assertion library, now requiring a commercial license for production use from v7 onward.

- Good, because extensive community documentation and the widest existing example base
- Good, because highly expressive chained assertions covering objects, collections, exceptions, and async code
- Bad, because v7+ requires a commercial license — unacceptable for a project committed to open-source tooling
- Bad, because adopting it creates a recurring license obligation for a component that can be replaced by open-source alternatives without meaningful loss of capability

### TUnit

A newer .NET test framework built on source generators and the Microsoft.Testing.Platform.

- Good, because source-generator-based discovery is faster than reflection-based runners at scale
- Good, because open-source and designed for modern .NET
- Bad, because newer and less battle-tested than xUnit; community resources, CI integrations, and IDE support are maturing
- Bad, because switching from xUnit would require rewriting existing test patterns; the benefit does not outweigh the migration cost at this stage

### xUnit built-in Assert

The assertion methods included in xUnit itself (`Assert.Equal`, `Assert.Contains`, etc.).

- Good, because zero additional dependency
- Good, because always version-compatible with xUnit
- Bad, because assertion messages are less informative than Shouldly's — failure output requires manual inspection to understand the discrepancy
- Bad, because the static `Assert.X(expected, actual)` syntax is less readable than fluent extension methods

### NSubstitute vs. Moq

NSubstitute uses a natural substitution syntax (`Substitute.For<IService>()`, `sub.Method(arg).Returns(value)`) that mirrors how you would describe the interaction in English. Moq requires `Mock<T>` wrappers and `.Object` dereferencing for the substitute instance.

- NSubstitute good, because cleaner setup syntax reduces test boilerplate
- NSubstitute good, because verification syntax (`sub.Received().Method(arg)`) reads more naturally than Moq's `mock.Verify(m => m.Method(arg), Times.Once())`
- Moq bad, because the `mock.Object` indirection adds noise in test setup; NSubstitute instances are used directly

### WebApplicationFactory + Testcontainers vs. in-memory EF Core provider

- Testcontainers good, because real PostgreSQL catches query syntax issues, transaction behaviour, and migration correctness that in-memory providers silently ignore
- Testcontainers good, because test environment mirrors production database engine, eliminating a class of "works in tests, fails in prod" bugs
- In-memory EF Core bad, because it does not enforce relational constraints, does not execute raw SQL, and does not run migrations — it is a fake, not a real integration surface

### Vitest vs. Jest

- Vitest good, because it shares the Vite config with SvelteKit, avoiding a separate Jest + Babel + SvelteKit transform pipeline that frequently diverges from the production build
- Vitest good, because HMR-aware test execution provides a fast feedback loop during development
- Jest bad, because requires separate transform configuration to understand Svelte components; configuration drift from the Vite build pipeline is a recurring maintenance burden

### Playwright vs. Cypress

- Playwright good, because Microsoft-backed with active .NET and TypeScript investment; long-term support trajectory is strong
- Playwright good, because cross-browser testing (Chromium, Firefox, WebKit) in a single tool
- Playwright good, because trace viewer provides a recorded, step-by-step replay of test failures, making CI failure diagnosis dramatically faster
- Cypress bad, because historically limited to Chromium-based browsers for E2E; multi-browser support was added later and remains secondary
- Cypress bad, because Cypress Cloud (for CI parallelisation and test recording) is a paid service; Playwright's tracing is built-in
